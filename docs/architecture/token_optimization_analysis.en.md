# Design Analysis of Cloud Token Optimization and Quality Maintenance via Local LLM

## 1. Background and Challenges

The [agy_sample.py](../../agy_sample.py) script presents the following pattern:
1. **Cloud Architect (Gemini)**: Reads the entire `plan/*.md` and decomposes it into a detailed task list for the local environment.
2. **On-Device Builder (Gemma 4)**: Implements each decomposed task one by one through local inference via the Antigravity SDK.

This approach is an effective method for reducing tokens by delegating "massive context understanding" to the cloud and offloading "individual code generation" to the local LLM.
However, there is a quality trade-off: forcing a local LLM (7B-9B scale like Gemma 4) to write large-scale code from scratch often leads to inconsistencies in interfaces between components and library types, paradoxically increasing the number of correction loops.

---

## 2. Comparative Review of Token Consumption Patterns

| Development Approach | Cloud Token Consumption | Local Inference (RTX 3060) | Implementation Quality / Consistency | Optimal Use Cases |
|---|---|---|---|---|
| **A. Full Cloud (Jules Only)** | **High** (Hundreds of thousands to millions of tokens) | None | **Extremely High** | Large-scale refactoring, initial repository setup |
| **B. agy_sample.py Method (Cloud Planning + Local Implementation)** | **Low to Medium** (Thousands to tens of thousands of tokens for plan decomposition) | **Maximum** (All code generated locally) | **Medium** (Prone to interface mismatches between components) | Mass production of boilerplate scripts or independent utility functions |
| **C. Hybrid Optimization Method (Recommended for this project)** | **Minimal** (Have Jules generate the initial PR just once) | **Medium** (Only test-driven local patches and fine-tuning) | **Extremely High** (Overall skeleton is secured by Jules; details resolved by real-device verification) | ML/RAG pipelines with high dependency on GPU/CUDA and external libraries |

---

## 3. Best Practices to Achieve Both Token Reduction and Quality Maintenance

### 3.1 Use Local LLM for "Skeleton + Local Repair" Instead of "Generation from Scratch"
- **Challenge**: Instructing a local LLM (Gemma 4) to "write the entire serial pipeline of Qwen2.5 Logit extraction and Ruri search" often results in tensor shape errors and missing import exceptions.
- **Solution**:
  - Class design, function signatures, and basic mock tests are **perfectly generated by Jules (Cloud) in a single PR**.
  - The local LLM (Gemma 4) is instructed **only on "the specific point of failure in pytest" or "adding a parameter/type assertion to a specific function"**.
  - This minimizes cloud API token consumption (limited to one PR) while completely covering the local LLM's weakness (difficulty in maintaining global consistency).

### 3.2 "Surgical Slicing" of Prompt Injection Context
Instead of passing the entire specification as in [agy_sample.py](../../agy_sample.py), minimize the prompt passed to the local LLM:
```python
# Bad example: Putting the entire plan/*.md and all related files into the prompt (Compresses VRAM & induces hallucination)
prompt = f"{full_plan_text}\n{entire_repo_context}\nFix the bug."

# Good example: Injecting only the failed stack trace + scope of the target function (20-50 lines)
prompt = f"""
[Target File]: {target_file} (L40-L65)
[Pytest Error]:
{test_failure_traceback}

[Instruction]:
Adjust the tensor slicing or prefix to resolve the error above. Keep other lines unchanged.
"""
```

### 3.3 Conclusion on Return on Investment (ROI)
1. **Use of Cloud (Jules)**: Limited to "architectural skeleton" and "test definition" (1 PR per feature).
2. **Use of Local (Gemma 4 / agy CLI)**:
   - Self-repair loops upon test failure (**Token cost is $0** regardless of dozens of attempts).
   - Expanding comments and documentation.
   - Resolving coding convention and linter errors.
